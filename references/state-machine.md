# 状态机

点餐主流程按状态单向推进，每状态末尾暂停等待用户明确选择。收到用户回答后只能推进到下一状态或在本状态内修正，不跳步。

## 首轮规则

1. 收到点餐意图后，禁止连续多轮追问。立即基于默认假设产出 1 套初步方案：1 人 / 人均 30-40 元 / 就近到店自取。
2. 初步方案可先为结构性方案（如「板烧鸡腿堡 + 中薯条 + 饮料，预估 ¥35 左右」），标注预估；若已有收藏门店（query-nearby-stores searchType=1 有返回），可取最近收藏门店调 query-meals 生成真实菜单价方案。
3. 方案末尾只附一个追问，按优先级补缺：履约方式 > 人数预算 > 口味。
4. 用户给出任一约束后，下一轮更新方案再追问剩余缺口，每轮最多一个问题。
5. 隐式触发（用户只说品类，如「巨无霸多少钱」）：默认按麦当劳执行，方案中附一句「按麦当劳为你搭配」轻确认，不加额外一轮。
6. 首轮先静默调用 now-time-info 判断时段：10:30 之前早餐池优先，之后正餐池。

## 状态定义

| 状态 | 进入条件 | 核心动作 | 暂停点 |
|---|---|---|---|
| S0 意图与初步方案 | 主触发或隐式触发 | now-time-info 判时段；按首轮规则出初步方案 | 展示方案 + 一个追问 |
| S1 履约与门店 | beType 确定 | 门店链路查询 | 用户选定门店或地址 |
| S2 需求细化 | 门店确定 | 补齐人数/预算/口味三要素 | 用户确认三要素 |
| S3 菜单与搭配 | 三要素齐备 | query-meals；执行 combo_builder.py；呈现 2-3 套搭配 | 用户选一套 |
| S4 领券 | 方案初选 | 列券 → 用户选定 → auto-bind-coupons → query-store-coupons 确认入包 | 用户同意领券 |
| S5 比价 | 领券完成 | query-store-coupons；预筛；试算；compare_plans.py；比价表 | 用户选最终方案 |
| S6 细节确认 | 最终方案选定 | 特调、随单购、餐具、备注、预约；明细有变则复核 | 用户硬确认 |
| S7 下单 | 硬确认通过 | 选取餐方式（orderType=1）；create-order | 引导支付后停住 |
| S8 支付跟踪 | 用户回复支付状态 | query-order | 报告状态与后续 |
| S-R 复购 | 复购触发 | 还原上次订单，重新试算，硬确认后下单 | 硬确认 |

## S0 意图与初步方案

调用 now-time-info 获取当前时间，判断早餐（10:30 前）或正餐池。按首轮规则生成初步方案并附一个追问。话术示例：

「按默认先给你配一套：1 人、人均 30-40 元、到店自取——板烧鸡腿堡套餐 + 小食，预估 ¥35 左右（最终以门店实价和券后价为准）。想怎么吃？①到店自取 ②得来速 ③麦乐送 ④团餐」

## S1 履约与门店

先确定 beType：到店自取=1，得来速=5，麦乐送=2，团餐=6。参数细则见 `references/param-matrix.md`。

**到店链（beType=1/5）**：query-nearby-stores(beType, searchType=1) 查收藏餐厅。无收藏时改 searchType=2，需城市与关键词；两者缺失则停下问用户，告知「按你所在城市搜索」。返回门店列表（≤5 家，带距离/营业时间/reservationTimeOptions，today=true 标「今天」）等用户选择。beType=5 时展示并记住 beCode，提示「得来速门店已记录车道编码，下单时自动使用」。

**外送链（beType=2/6）**：先 delivery-query-addresses 查已有地址。有则列出等用户选定；无则引导用户提供五要素（城市 / 联系人 / 手机号 / 地址 / 门牌号）后 delivery-create-address 新建，取得 addressId。然后 delivery-query-stores(beType, addressId) 取可配送门店（含 beCode），等用户选店。addressId 缓存，后续 calculate-price 与 create-order 透传。

搜索无结果时明确说「没找到门店」，请用户提供城市或商圈关键词；禁止虚构门店。

## S2 需求细化

纯对话状态，无 MCP 调用。若 S0 已收集齐三要素则合并到 S3 前的一句话确认。一句话复述「N 人 / 预算 X 元 / 口味偏好」请用户确认或纠正。若首轮已问过且用户已给，不重复问。

## S3 菜单与搭配

1. query-meals(storeCode, orderType, beType[, beCode]) 取菜单。团餐场景必须以 beType=6 返回的菜单为准。
2. 将菜单字段（code/name/priceCent/category/tags）与人数/预算/口味组装为 JSON，通过标准输入执行 scripts/combo_builder.py，输出 ≤5 套候选。
3. 呈现 2-3 套搭配，每套标注结构说明与菜单价预估（人均/总价），明确「券后价下一步算」。
4. 商品特调标注：query-meal-detail 返回 supportModify=true 的商品名称后标【可特调】；不主动展开特调列表，用户问再展开。
5. 用户说「都不满意」→ 微调口味/预算在本状态重生成。
6. 脚本失败时按 SKILL.md 脚本降级执行，输出声明「估算价」。

## S4 领券

固定顺序，未展示券列表前不得发起领取：

1. available-coupons() 查麦麦省可领券，列出每张券的面额 / 门槛 / 有效期 / 适用范围。
2. query-my-coupons(page=1, pageSize=50) 展示卡包存量，明确声明「卡包里的券是否适用于这家店，以下一步门店券查询为准」。
3. 暂停征询：是否一键领取（auto-bind-coupons()）。
4. 用户同意后 auto-bind-coupons() 领取。
5. 进入 S5 后由 query-store-coupons 确认新券入包。
6. 麦麦省无券可领时跳过本状态直接进入 S5。

## S5 比价

按 `references/pricing-engine.md` 执行：query-store-coupons 取券 → 硬过滤与打分预筛出 3-5 个候选 → 每候选 1 次 calculate-price（≤4 次，无券基线不消耗）→ 汇总结果执行 scripts/compare_plans.py → 呈现比价表（原价/用券/券后实付/省多少/折扣），最优行标注，脚注声明试算时间与「以支付页实时价为准」及配送费口径。用户选最终方案后进入 S6。

用户对方案都不满意 → 退回 S3 重生成（券已在卡包，不重复领券）。

## S6 细节确认

1. 需要特调时调 query-meal-detail(code)，按 `references/param-matrix.md` 的 selectedKey/unselectedKey 整组规则组装 modification。
2. 确认随单购（withOrder，来自 query-meals）、餐具（needTableware）、备注（remark，≤50 字，仅 orderType=2 引导填写）、预约时间（reservationDate，可选）。
3. 明细相对 S5 有变（加了特调/随单购）→ 用剩余预算中的最终复核 1 次 calculate-price 再展示。
4. 展示最终订单明细与券后实付价（已分转元），等待硬确认。

## S7 下单（硬确认闸门）

**硬确认词表：**

- 有效确认：确认下单 / 下单吧 / 就这套 / 就这个，买。
- 无效确认（不得触发下单）：嗯 / 随便 / 可以吧 / 你看着办 / 好的。

收到无效确认时，复述四项后再问一次：

1. 最终券后价（元）
2. 履约方式与门店名
3. 商品明细
4. 外送时：地址与备注

四项均获明确表态后才调用 create-order。create-order 参数与最后一次 calculate-price 完全一致；若试算与下单间价格有变，回到本闸门重新确认。

orderType=1 时先让用户从最后一次 calculate-price 返回的 takeWayList 选取餐方式；S1 已定 beType=5（得来速）时直接取列表中对应项，不再重复询问。

create-order 成功后按工具指引引导：「您可以通过支付链接扫码或者打开麦当劳 APP 完成支付，支付完成后请回复『支付完成』或『支付失败』，会帮您查询最新的订单状态。」然后停住。只复述 create-order 真实返回的订单号等信息。

## S8 支付跟踪

用户回复后 query-order(orderId) 查最新状态。支付成功：报告状态并提醒取餐码/配送信息，可顺带提示满意度奖券（query-survey-coupon，orderId 为该真实订单号）。支付失败：给两条路——继续等待重付，或取消（先询问取消原因再 cancel-order(orderId, cancelReasonCode)，原因码：1=改主意了，2=重复下单，3=点错了/点多了/点少了，4=地址/电话填错了，5=送达时间选错了，-1=其它）。长时间未回复支付状态时提醒一次，不主动臆断。

## S-R 复购分支

触发：「再点一次上次那个」「跟昨天一样」。

1. order-list() 查历史订单，取最近一笔餐品订单（到店或外卖）。注意：mall-order-list 是积分商城订单，不可用于复购餐品；复购只走 order-list。
2. query-order(orderId) 还原商品明细（productCode/quantity/特调等）。
3. 按本次履约方式和门店重新 calculate-price，明示「当前价为实时试算，可能与上次不同」。
4. 进入 S7 硬确认闸门（价格/履约/门店/明细逐项）。
5. create-order，后续同 S8。

无可复购订单时如实告知，转入全新点餐流程（S0）。

## 回退规则

- S5 用户都不满意 → 退 S3 换口味/预算重生成，不重做领券。
- S6 改动明细 → 仅重算受影响的 calculate-price（最终复核预算内）；预算耗尽时用菜单价估算并明确标注「未经系统试算」。
- 用户中途换履约方式 → 退 S1 重走门店链路，beCode 必须重新获取。
- 试算中用户改了商品集合 → 已有候选作废，试算次数重新计数；仅改口味标签等非商品约束不重置预算。
